---
title: Change verification
description: How a change is checked against production after it deploys.
---

For every pull request on a connected repository, the agent reads the diff, writes down what success and failure would look like as checks against your telemetry, and runs those checks after each deploy — for the first 10 minutes, then at an hour, a day, and three days. The result is one review comment on the pull request, kept current until the change is verified. It is on for every connected repository; there is nothing to set up beyond the deploy signal below.

## When a pull request opens

The agent reads the diff and writes the checks. Two kinds: the effect the change promises (a latency fix should drop latency; if it doesn't, that counts as a regression too), and what the touched code could break — the endpoints, queues, and jobs that call through it. It measures each of those signals while the pull request is still open, so every check compares after-deploy against a real baseline rather than an invented threshold. A check with too little traffic on either side to judge is not counted against the change.

The plan is posted as one review comment on the pull request:

```text
Batches Redis writes on checkout so p95 drops.

Watching
- [ ] checkout p95 latency below the pre-merge baseline
- [ ] checkout 5xx rate holds
- [ ] order-confirmation queue lag holds

Would fail it
- p95 not below baseline by the 24h checkpoint
- 5xx above 2× baseline at any checkpoint
- queue lag over 60s at any checkpoint

`changes/acme--api--pr-42` · armed — awaiting merge
```

The last line is the status, kept current until the change is done. That review is the only thing OnePatch posts on a pull request. It edits the same review in place — never a second review, never an issue comment — and it never approves, requests changes, or blocks a merge. The plan is information, not a gate.

The plan is written from the diff when the pull request opens; if the change evolves substantially before it merges, ask the agent to revise it.

Changes that cannot alter runtime behavior — docs, lockfile bumps, formatting, comments, CI config, tests — are skipped without a word on the pull request; the reasoning is in the app's chat for that pull request. When in doubt, the agent verifies: a one-line config change is exactly the kind of diff that takes production down.

## After the merge

Verification waits for the deploy — the first successful deploy into each of your environments after the merge, in the order you deploy them (staging, then production, say). OnePatch assumes that deploy carries the change. The clock starts at the deploy, never at the merge; how OnePatch recognizes a deploy is under [What it needs](#what-it-needs).

The checks then run continuously for the first 10 minutes after that environment's deploy, then at 1 hour, 24 hours, and 72 hours — the soak. For a risky change — a data migration, an auth or payment path — the agent lengthens the soak and says so in the plan.

The status line is one of these — the first three in sequence (it returns to `awaiting deploy` between environments), then one ending:

| Status | Meaning |
|---|---|
| `armed — awaiting merge` | Plan posted; the pull request is still open. |
| `armed — awaiting deploy` | Merged; no deploy seen yet in the next environment. |
| `soaking · production · 2 of 4 checkpoints clean` | Deployed; checks holding so far. |
| `verified · production — soak clean. Monitor retired.` | Every check held through the last checkpoint. The environment named is the last one the change reached. |
| `regression · production — <reason>. Incident opened.` | A check tripped. |
| `inconclusive — no deploy observed within 30 days. Monitor retired.` | Merged, but never deployed where OnePatch could see it. |
| `retired — PR closed without merging.` | Nothing to verify. |

The environment appears when your deploy signal labels one.

## When a check trips

A regression is an incident, handled like any armed monitor firing (see [Incidents and Slack](/incidents-and-slack)). Before blaming the change, the agent re-runs the check itself and looks for another explanation — a parallel deploy, a traffic shift, an upstream outage. If the evidence clears the pull request, the incident says so and resolves. If not, the review's status line names the environment and what tripped and links the incident, which names the check and the deployed commit; the agent proposes a revert or a fix-forward pull request. It proposes; you merge.

The author learns their change regressed on their own pull request.

## When it holds

A clean verdict is quiet by design. The agent ticks the review's checkboxes, sets the status line to `verified`, and deletes the temporary monitor that ran the checks. No incident, no Slack message, no row left on the Monitors screen. Nothing outlives a verified change but one line on its pull request.

## Where it shows up

- **The pull request** — the review, with its live status line.
- **Home** screen — pull requests the agent opened for you carry a `verification` footer with the status line.
- **Monitors** screen — a `changes/…` row per pull request in flight, with its phase and status. The row goes away when the change reaches a quiet verdict; on a regression it stays until the incident resolves, reading `regression — see the incident.`
- **Deploys** dashboard — the one the agent builds when it works out your deploy signal; a verdict column per version and environment for the last 30 days, blank where no change was verifying that deploy.

## What it needs

- **A connected GitHub repository.** Verification covers every repository you have connected, for pull requests opened after it was connected — drafts included.
- **A deploy signal.** OnePatch has to know which of your CI/CD events means "this shipped", as opposed to a test run going green — for one team it is a job named `deploy`, for another a Vercel deployment status, for another a release workflow on `main`. The agent works this out from your GitHub pipeline events (workflow runs, deployment statuses, commit statuses) and workflow files, and settles on it once. Until then each plan says so; ask the agent to re-arm any plans written before the signal was set, and pull requests opened afterwards verify on their own. If none of those events flow, ask the agent to set a deploy signal by hand.

<Note>
If your deploys happen where GitHub cannot see them, the agent may open one pull request adding a single line to the end of your deploy step: a `curl` that reports "deployed" to the telemetry endpoint your apps already use. It adds about a second, touches nothing else, and you can delete it any time. If you decline, it uses the best signal it can see and does not ask again.
</Note>

## Limits and turning it off

Up to 20 changes verify at once. A pull request that opens past that limit is picked up as capacity frees — a few every couple of minutes, in no particular order — or skipped if it is still waiting after three days.

To stop verifying a repository, or stop altogether, ask the agent. Stopping applies to pull requests opened from then on; changes already in flight keep running. If you exclude a repository, repositories you connect later have to be added back explicitly. To change what a plan watches or how long it soaks, ask — the agent edits the plan in place.
